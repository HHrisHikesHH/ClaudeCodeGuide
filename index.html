    Tight Loop

    Ship more with less context. A field guide to Claude Code for solo developers: keep the window small, give Claude a check it can run, and approve the irreversible yourself.

    13 sections, 11 prompts, 9 sources

    Illustrative session

    An illustrative Claude Code session: plan a sign-in feature in plan mode, implement it with tests passing, run /verify, then commit and open a pull request.

    01verified 2026-10-30

    The 10 rules

    1. Context is the scarce resource. Quality drops as it fills. /clear between unrelated tasks.
    2. Give Claude a check it can run (tests, build, linter, screenshot). That is what lets you stop babysitting.
    3. Explore → plan → code → commit. Skip the plan if you can describe the diff in one sentence.
    4. Be specific: name files with @, describe the symptom, state constraints, point to an existing pattern to copy.
    5. Keep CLAUDE.md short. For each line ask: “would removing this cause mistakes?” If not, cut it.
    6. Research in subagents, implement in the main session.
    7. Two failed corrections → /clear and re-prompt with what you learned.
    8. Git is the safety net. Commit before big tasks. Checkpoints do not track Bash changes.
    9. You gate the irreversible: schema changes, deletes, new dependencies, auth, payments, deploys, secrets.
    10. Fewer, vetted extensions. Third-party plugins and MCP servers run with your permissions.
    02verified 2026-10-30

    The core workflow

    1. Explore in plan mode (Shift+Tab or claude --permission-mode plan): read code, no edits.
    2. Plan: ask for a plan, edit it with Ctrl+G.
    3. Implement against the plan, running tests as it goes.
    4. Verify with evidence (test output, screenshot), not “looks done”. Run /verify against the running app.
    5. Commit and open the PR. Review the diff yourself.

    Larger features: have Claude interview you and write SPEC.md, then execute in a fresh session. Unattended runs: set the check as a /goal condition or a Stop hook so it can’t finish until the check passes.

    I want to build [description]. Interview me in detail using the AskUserQuestion tool. Cover technical implementation, UI/UX, edge cases, concerns and tradeoffs; skip obvious questions. Keep going until everything is covered, then write a complete spec to SPEC.md. Name the files and interfaces involved, what is out of scope, and an end-to-end verification step.

    Staying in the loop (permissions & gates)

    Ask first, in every mode

    • Schema
    • Deletes
    • Dependencies
    • Auth
    • Deploy

    Your ask-first list stays on in every mode. Enforced by your CLAUDE.md, deny rules and hooks, not by the mode.

    ModeBehaviorUse for
    ManualAsks before edits/commands/MCPUnfamiliar or risky code
    PlanRead-only analysisDesign, estimates, unknown codebases
    AutoA classifier reviews actions and blocks risky ones; default start mode on recent versions (v2.1.283+)Routine work
    dontAskOnly pre-approved tools, denies the restScripts / claude -p

    Recommended for you: plan mode to design → allowlist + auto for routine edits → a hard ask-first list for anything irreversible. Deterministic rules (deny rules, hooks) beat CLAUDE.md advice. Avoid --dangerously-skip-permissions outside a sandbox/container.

    ## Ask me first (never do silently)
- Schema/migration changes, data deletion, destructive git (force push, reset --hard)
- Adding/upgrading dependencies, changing build/CI config
- Auth, payments, permissions, secrets/env handling
- Deploys, anything touching production or paid external services
- Public API/contract changes
For these: explain the change and risk in 3 lines, then wait for my OK.

    Hooks: ask Claude “write a hook that blocks writes to the migrations folder” or “runs eslint after every file edit”, then review with /hooks.

    macOS setup

    $ curl -fsSL https://claude.ai/install.sh | bash     # native installer (or: brew install --cask claude-code)
$ cd your-project && claude                           # then /login with your Pro account

    Install commands change often: confirm on the official setup page (see Sources). If an ANTHROPIC_API_KEY env var is set you may be billed per token instead of using your Pro plan. Check with /usage.

    First 10 minutes in any project

    • /init generates a starter CLAUDE.md. Prune it. /context confirms what loaded. /doctor suggests cuts.
    • Set up a custom status line that shows context usage (docs: “statusline”).
    • /permissions to allowlist safe commands (tests, lint, git commit); /sandbox for OS-level isolation.
    • Install gh (GitHub CLI): the most context-efficient way for Claude to handle issues and PRs.

    Desktop app vs CLI

    CLI: fastest, scriptable (claude -p), full feature set. Desktop: visual multi-session management, optional worktree per session. Keep your editor open in another window to review diffs; sessions are shared per project folder.

    08verified 2026-10-30

    Prompt library

    Pick a stack

    I’m a solo developer building [app]. Constraints: [budget, hosting, timeline, skills]. Propose 2–3 tech stacks with trade-offs (build speed, ops burden, cost, hiring/maintenance, lock-in). Recommend one, then stop and wait for my decision. Don’t write code yet.

    Scaffold

    Read SPEC.md. Scaffold the project with the agreed stack: folder structure, lint/format/typecheck, a test runner, one passing smoke test, a README with run/test commands, and a first CLAUDE.md under 60 lines. Run everything and show me the output.

    Feature from spec (fresh session)

    Implement [feature] per SPEC.md. Follow the patterns in @[example file]. Write tests first for the main paths and edge cases. Run lint, typecheck and tests until green. Show evidence. Don’t touch anything outside this scope; flag anything that needs my approval.

    Debug

    Symptom: [what happens]. Expected: [what should]. Likely area: [path]. Write a failing test that reproduces it, find the root cause (don’t suppress the error), fix it, and show the test passing.

    Database change

    Propose the schema change for [goal] and the migration (up and down). Explain data-loss risk and locking impact. Do NOT apply anything. After I approve, run it on the dev database only and show the result.

    Safe refactor

    Refactor [module] to [goal]. First add characterization tests for current behavior. Then change in small steps, running tests after each, one commit per step. Stop if a test changes meaning.

    Review (fresh eyes)

    Use a subagent to review the current diff against SPEC.md. Report only gaps affecting correctness, security or stated requirements. Skip style opinions.

    Security pass

    Use a subagent to audit [path] for injection, authn/authz flaws, secret leakage, and insecure data handling. Give file:line references, severity, and a suggested fix. Don’t change code.

    Research a choice

    Use subagents to research [question]. Check current official docs (use Context7 if available). Return: options, trade-offs for my case, a recommendation, and sources. Max 25 lines.

    Handoff before /clear

    Write HANDOFF.md: goal, decisions made and why, files changed, what’s done, what’s next, commands to run tests. Keep it under 40 lines.

    Prune CLAUDE.md

    Review CLAUDE.md. Remove anything you can infer from the code or already do correctly; move rarely-needed workflows into skills; keep it under 100 lines. Show the diff.

    CLAUDE.md starter

    # [Project]: one-line purpose
## Commands
- dev: [cmd] · test (single): [cmd] · lint/typecheck: [cmd] · build: [cmd]
## Conventions (only what differs from defaults)
- [e.g. ES modules, named exports; API errors use {code,message}]
## Workflow
- Typecheck + run relevant tests after code changes. Prefer single tests over the full suite.
- Branches: feat/x, fix/x. Commit messages: conventional.
- When compacting, keep modified files and test commands.
## Ask me first
- (paste the Ask-first block from section 04 (Permissions))

    Skill (.claude/skills/fix-issue/SKILL.md)

    ---
name: fix-issue
description: Fix a GitHub issue
disable-model-invocation: true
---
Fix GitHub issue $ARGUMENTS: read it with `gh issue view`, find the code, write a failing test, fix, run lint/typecheck/tests, commit, open a PR.

name: security-reviewer
description: Reviews code for security vulnerabilities
tools: Read, Grep, Glob, Bash

    Keep this guide current

    Routine (monthly, or when a release catches your eye): open Claude chat with web search on → attach this file → paste the prompt below. It returns minor changes as a short list. Only if something major turns up does it give you an edit prompt to paste into Claude Code (run from the repo folder holding index.html).

    You are auditing my Claude Code guide. The attached HTML file is the guide. Web search is on.
1. Read the guide: note each section’s "verified" date and the Update Log.
2. Search for what changed since the oldest verified date. Official first: code.claude.com/docs (best-practices, costs, features overview, llms.txt index), Claude Code releases/changelog (github.com/anthropics/claude-code), claude.com/pricing, Anthropic news. Then reputable community sources (the guide’s Sources section plus anything new with real traction). Also check that every command, flag, install line and plugin name in the guide still exists.
3. Classify each finding.
MAJOR = materially affects my work, time or money: new/removed tools, models or features; changed or deprecated commands, flags, defaults; a new official best practice that beats the guide; pricing, plan-limit or token-cost changes; a security problem with something the guide recommends.
MINOR = everything else.
4. Output exactly:
a) Verdict: "NO MAJOR CHANGES" or "MAJOR CHANGES FOUND".
b) Minor changes: one line each with a source URL. Report only; propose no edits.
c) ONLY if major changes exist: for each, what changed, source URL, guide section affected. Then ONE ready-to-paste prompt for Claude Code, in a code block, that edits ./index.html in place.
d) If there are no major changes, stop after (b). Do not write an edit prompt and do not rewrite the HTML.
Rules: separate verified fact from community opinion; mark anything unconfirmed "unverified"; never invent; keep it short.
The Claude Code edit prompt you write must: edit only the affected <section> elements (each has a stable id, a data-v="YYYY-MM-DD" attribute and a visible .stamp "verified YYYY-MM-DD" text; update both); keep the file self-contained, keep all ids, classes, data-* attributes and the <script> intact; new prompts go in as <article class="tile" data-cat="…"> inside #prompts; add an <li> to the Update Log list #lg (date + what changed); update Sources if needed; then show git diff --stat and stop for my review. No commits.

    Why this works

    Each section carries a data-v date and a visible “verified” stamp, so the auditor knows what’s stale. Commit the file to git; the diff after each update is your changelog.
